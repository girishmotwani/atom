# General Onboarding Prerequisite Flow Repair Brief

## Issue

General onboarding discovers missing commands by executing them, which presents
expected absence as repeated failures even when a healthy hidden Atom venv exists.
The workflow also failed to establish the participant's active client: source and
observer checks used 1.0.107 while the continued session reported 1.0.5. A later
head-ended pipeline hid a real writer refusal and the agent continued afterward.
The writer guard worked; its implementation is not the defect to repair.

The developer requested general /atom:init repair and an issue/approach summary
before work. The stopped rehearsal remains Inconclusive, not a basis for a final
expense-example design or a claim that one client/model caused every deviation.

## Proposed Scope

- Make critical prerequisite ordering and stop conditions explicit in the init
  skill itself, with detailed shared procedure in bootstrap.md.
- Establish the active Copilot client's reported identity, not merely the version
  of another executable. Use the existing documented support requirement; do not
  invent a new pin or claim all supported versions were tested. Ask one focused
  question if the active identity is unavailable or ambiguous. No automatic update.
- Determine whether candidate commands/interpreters/packages are available before
  attempting help for forms known to be absent. Report absence as a prerequisite
  state rather than a successful runtime check or a failing installation.
- Preserve resolution priority and existing working/editable installations. Reuse
  verified command roles, including the known safe Linux venv, without reinstalling
  or repeating discovery after both forms have been established.
- Only genuine absence permits an installation proposal. Explain required tools
  and obtain explicit consent before any provisioning. Missing system prerequisites
  receive clear guidance; this repair does not add Python/Go/system provisioning.
- Keep real command/import failures, ownership checks, installation collisions,
  writer refusals and failing Go baselines visible. Never mask their exit status
  with head or treat a failed command as permission to install or continue.
- Keep artifact verification at supported help/actual authorized writes, not an
  invalid-target probe. Retain the normal module-local writer approval boundary.
- End onboarding with a next beat supported by the active client. File existence
  or skill-list discovery alone is not proof of a particular interactive alias.

Expected source scope is skills/init/SKILL.md, skills/atom/references/bootstrap.md,
their two packaged counterparts under tools/atom/assets, and directly related
README onboarding/prerequisite explanations. Preserve historical ledgers and
frozen trial recipes, the existing Windows setup-path opt-in, Linux isolated
installation policy and all pipeline gates. No runtime API, new executable,
state schema, plugin namespace, dependency or version change is proposed.

## Evidence Choice Recommendation

Reuse the recorded defects in prepared-rehearsal-report.md and the accepted
bootstrap-repair-report.md/bootstrap-boundary-report.md installation and reuse
evidence within their stated boundaries. The new uncertainty to check is the
availability-first discovery boundary, not whether the same package can be
installed again. This is a guidance repair for observed failures, not permission
to manufacture a Go algorithm spike or claim instructions enforce compliance.

Proposed bounded question:

Can the proposed availability checks identify the existing usable command forms
and explicit package absence in the available Windows and Ubuntu environments
without executing known-missing Atom commands or hiding real execution failures?

Before drafting the changed-flow spec, request approval for one non-installing
pass in each existing environment, capped at five minutes total and at most six
terminal invocations. Use supported command resolution/package-presence checks,
the known safe Linux venv checks before execution, and help only for existing
candidates. Do not create fixtures, environments or target files. Do not invoke
init, check, an invalid writer target, install/update commands or model sessions.
Record commands, statuses and full relevant diagnostics. Stop on uncertainty,
an unexpected failure, required provisioning or a materially different approach.

A successful pass supports only those discovery mechanics in the observed two
environments. Explicit absence should be returned as data, while genuine errors
must remain errors. An unexpected result is a blocker; do not force a successful
classification, broaden the search or silently change the procedure. Partial or
missing evidence is Inconclusive. Existing unsafe/partial-install safeguards are
retained and reviewed, not newly claimed to be comprehensively exercised here.

Alternative: first approve a new bounded model-driven onboarding experiment.
That would cost model calls and could assess actual agent route selection, but
would add another coached run before the known entry-flow issues are repaired.
Recommend the narrower no-model check now; any future compliance/usability claim
still needs separately approved observed validation with fixed client/model/source.

## Gates And Validation

Approval of this brief selects evidence reuse and permits only the bounded checks
above. Present the actual discovery result and stop at the evidence gate. Only
after that result is accepted, draft and present the short repair spec at its own
approval gate before editing shipped guidance. Changed assumptions, provisioning
or runtime work return to a gate. Requesting the repair waives no gate.

After spec approval, implement the narrow guidance change and synchronize assets.
Use existing relevant onboarding/plugin/artifact-fallback/Windows-path tests,
python tools/check_links.py, byte parity checks and git diff --check. Preserve
existing Windows command forms and avoid new tests that merely assert prose
phrases. Static/documentation checks establish contract/parity, not actual agent
compliance, all-client compatibility or a repaired live workflow. No root Go check
is appropriate for this Python tooling repository.

No installer execution, plugin refresh, profile/PATH/auth change, model batch,
rehearsal restart, expense implementation, commit, push or merge is approved by
this proposal. The existing trial and active participant session remain stopped.
