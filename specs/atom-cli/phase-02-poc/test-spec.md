# Test Spec -- Phase 2: `atom poc`

This is a retrospective test spec for Phase 2: `atom poc new`, `atom poc run`, and `atom poc list`. The tests already exist; this document maps behaviours B35-B70 to the named tests that pin them.

B67-B70 were added after the original Phase 2 design text. They are included here only where tests or the current design spec reference them.

**Suite:** 172 tests passing, 93% statement coverage.

```
python -m pytest tests -v --cov=atom --cov-report=term-missing
```

## Tests that exist to prevent regression of a specific discovery

| Test | Discovery pinned | Why removing it would be dangerous |
|---|---|---|
| `test_never_uses_go_run` | `go run` flattens non-zero spike exit codes to `1`. | A later simplification back to `go run` would make Inconclusive look Refuted and would also blur compile failure with runtime failure. |
| `test_inconclusive_survives_as_inconclusive` | A built binary preserves exit `2`; `go run` does not. | This is the core Phase 2 finding. Without it, Atom could launder a valid third verdict into a false refutation. |
| `test_build_failure_is_reported_as_build_not_execute` and `test_execute_failure_is_reported_as_execute_not_build` | Build failure and runtime failure are different events that `go run` can conflate. | Removing these tests would let the report become less actionable while still returning a plausible non-zero result. |
| `test_scaffold_go_mod_pins_full_patch_version` | `go mod init` writes the toolchain's full patch version, observed as `go 1.23.4`. | A template could silently drift from the real toolchain output and recreate the bug the shell-out design avoided. |
| `test_library_spike_can_never_be_inconclusive` | `go test` does not provide Atom's three-valued command-spike vocabulary. | This limitation was created by a review decision. Removing the test would hide a known mismatch between library and command spikes. |
| `test_panicking_spike_is_crashed_not_inconclusive` | A panicking Go program exits `2`, colliding with Atom's Inconclusive code. | Without this test, a crash could be reported as a valid inconclusive answer and CI could go green on a broken spike. |
| `test_deliberate_exit_2_is_still_inconclusive` | Exit `2` is only a crash when it has the panic signature. | This protects the original verdict contract from an over-broad crash parser. |
| `test_crash_detection_needs_both_the_exit_code_and_the_signature` and `test_crash_detection_requires_a_stack_dump_not_just_the_word` | Panic detection needs both exit code `2` and a Go stack signature. | These controls stop Atom from treating ordinary output that mentions panic as a runtime crash. |
| `test_a_crashed_spike_did_not_answer` and `test_a_crashed_spike_makes_the_command_exit_non_zero` | A crash is not a verdict, so it refines B64. | These tests prevent the old rule, "ran means success", from hiding crashed spikes behind exit `0`. |
| `test_the_cli_runs_as_a_module_without_exploding` | Importing `atom.cli` is not the same as running `python -m atom.cli`. | The earlier suite missed a `NameError` caused by definitions below the `__main__` guard. Only a subprocess test catches that shape. |
| `test_stderr_is_rendered_before_stdout` | The retrospective spec audit found B48 had no direct test. | Removing it would leave a same-day rendering edit free to flip stdout and stderr order without failing the suite. |

## Gaps and Limitations

### Behaviours with no test still missing

None found after the B48 characterization test was added.

### Gap found and closed while writing this spec

| Behaviour | What happened |
|---|---|
| B48 | The first retrospective pass found no named test asserting that stderr is rendered before stdout on failure. `test_stderr_is_rendered_before_stdout` was then added to `test_report.py` and passed immediately. This was a characterization test pinning already-correct behaviour, not a RED-GREEN cycle. |

Writing this test spec retrospectively earned its keep by surfacing exactly one untested behaviour. The behaviour sat in report-rendering code that had been edited the same day, so the missing test was not theoretical risk.

### Behaviours tested only indirectly or partially

| Behaviour | Limitation |
|---|---|
| B39 | The scaffolded `main.go` is inspected for `package main`, `func main()`, and the question. The test does not run the generated Go program to prove it exits `0`. |
| B41 | README sections and question are asserted. I did not find a test that asserts the created date is present. |
| B61 | Missing and empty `poc/` are covered. I did not find a test for an unreadable `poc/` returning an empty list. |
| B62 | `poc list`, `poc new`, and `poc run` are exercised through success, usage-error, or help paths. I did not find a successful end-to-end CLI test for `poc new` or `poc run`. |
| B63 | Usage errors are covered, and crash failure is covered through `_exit_code_for_spike`. I did not find a direct CLI test for `go mod init` / `ScaffoldError` mapping to operation-failed exit `1`. |
| B65 | The contract is pinned by exit-code tests plus renderer tests, not by one test that runs the command and asserts verdict text with process status. |
| B66 | JSON rendering is covered for `poc list` and spike-result renderer fields. I did not find a direct CLI test for `atom poc run --json` emitting the full `SpikeResult`. |

### Fakes that may not match reality

| Area | Limitation |
|---|---|
| `FakeGoModInit` in `test_scaffold.py` | The fake writes `go 1.23.4` to model the observed toolchain output. It does not run the local `go mod init`. |
| `ScriptedRunner` in `test_spike.py` | The fake classifies command tuples and creates a fake binary file. It proves Atom's orchestration and cleanup logic, not the real Go compiler's behavior. |
| Panic detection tests | The panic signature is hard-coded from an observed Go panic. These unit tests do not crash a real Go binary. |
| Library spike verdict tests | The test can simulate `go test` returning `2` to pin Atom's Unknown fallback, even though the design says normal `go test` success/failure gives only `0` or `1`. |
| CLI subprocess tests | B70 runs Python's CLI entry point in a subprocess. It does not run a real Go spike. |
